# DECISIONS — технические и геймдизайнерские решения

| D-001 | Код живёт внутри места Studio (без Rojo); документы — на диске в `TRAP_LAB/docs`. Место сохраняется через `save_place`. | MCP пишет скрипты в Studio напрямую. |
| D-002 | Модели препятствий строятся процедурно из Parts в общем модуле `ObstacleModels` (сервер и клиентский призрак используют одни и те же билдеры). Blender используется для иконок/рендеров; импорт мешей — только если найдётся рабочий путь. | `AssetImportService` недоступен через MCP, загрузка мешей требует Open Cloud/ручного импорта. **Противоречие ТЗ 4.3 (оригинальные модели в Blender) ↔ реальность окружения: зафиксировано, не скрыто.** |
| D-003 | Игрок получает стартового NPC «Starter» бесплатно. | Иначе цикл при 0 Rebirth нельзя начать, если в ротации NPC-магазина нет дешёвого NPC. Это не новая механика, а стартовое владение. |
| D-004 | Ротация обоих магазинов детерминирована: `slot = floor(os.time()/300)`, `Random.new(slot*salt)`. Сервер — источник истины; клиент получает готовый список и `nextRefresh`. | Одинаковый ассортимент у всех игроков и серверов без MessagingService. |
| D-005 | Движущиеся препятствия управляются сервером одним Heartbeat-циклом: позиция = f(`workspace:GetServerTimeNow()`, параметры). NPC-AI предсказывает ту же функцию. | Детерминированный тайминг; один цикл вместо сотен скриптов. |
| D-006 | У каждого препятствия есть `entry` (задняя кромка) и `exit` (передняя кромка) в локальных координатах (вперёд = -Z). Граф трассы: связь A->B, если расстояние exit(A)->entry(B) <= `MaxGap`, подъём <= `MaxStepUp`. Этапы = узлы кратчайшего пути Start->Finish. | Основа для проверки трассы, контрольных точек и маршрута NPC. Это эвристика, не гарантия проходимости. |
| D-007 | Декорации — отдельный слой: без коллизии, не считаются в лимите объектов трассы, имеют свой лимит. | ТЗ 17: косметика не мешает прохождению. |
| D-008 | Лимит активных NPC: 1,2,...,10 (по Rebirth 0..9), жёсткий потолок 10 на игрока и 24 на сервер. | ТЗ 5.2/10.7: рост лимита с разумным пределом. |
| D-009 | 8 участков, каждый — клетка 260x420; зона строительства растёт от фиксированного старта вперёд и в стороны симметрично. | Расширение не двигает старые постройки (ТЗ 13.2). |
| D-010 | Если DataStore недоступен (Studio без API Services), используется мок-хранилище в памяти с тем же интерфейсом; в логе и в UI явно «данные не сохраняются». | Тесты логики сохранения без реального DataStore; честная индикация. |
| D-011 | Удаление построек запрещено при Rebirth; если лимит ниже числа построек, постройки остаются, новые не ставятся. | ТЗ 13.2. |
| D-012 | Реквесты клиент->сервер идут через RemoteFunction (ответ `{ok, err, ...}`), пуши сервер->клиент через RemoteEvent. Сервер не вызывает клиента через Invoke. | Простая обработка ошибок UI, безопасность. |
| D-013 | Robux-покупки не добавляются, пока нет реальных Game Pass/Product ID (ТЗ 23: не создавать фиктивные покупки). | Честность. |

| D-014 | Награды NPC копятся в течение попытки и выплачиваются ОДИН раз при её завершении (идемпотентный ключ `npcS:<runId>` / `npcF:<runId>`). При выходе владельца, отмене, смене версии трассы или остановке сервера попытка завершается и выплачивает уже подтверждённые этапы. | ТЗ 11, 19: один платёж за этап/попытку; прогресс не теряется. |
| D-015 | Этап считается пройденным, когда сервер видит NPC рядом с точкой выхода этапа (6,5 студа) строго по порядку; бонус финиша только если подтверждены ВСЕ этапы. | ТЗ 10.5/10.6: серверная проверка, без выдуманного прохождения. |
| D-016 | Детектор падения — Spherecast вниз + 2 подряд срабатывания, цели «пол ямы / земля» (имя BuildZone/Land/Ground или тег TL_Ground). | BUG-004. |
| D-017 | NPC отказывается от прыжка, физически превышающего его дальность/высоту (WalkSpeed·время полёта·0,9), с причиной `cannot_cross`; не телепортируется и не «пролетает». Скорость перед коротким прыжком снижается. | ТЗ 10.6. |
| D-018 | Провал восстановления после спотыкания = настоящее падение (кувырок + боковой импульс), успех = возврат к центру; шанс = Recovery/12. | ТЗ 7.7: Recovery не делает NPC неуязвимым. |

## Противоречия/неоднозначности ТЗ
- (4.3 vs окружение) см. D-002.
- (5.2 «каждый Rebirth увеличивает лимит NPC» vs «разумный технический предел») — лимит растёт до 10 при Rebirth 9, дальше фиксирован; MaxRebirth = 10.


## D-019 (2026-11-15) — «маленькая трасса и NPC» реализована как ОТНОСИТЕЛЬНЫЙ масштаб
Запрос пользователя: трасса и NPC должны выглядеть маленькими (множитель x0,5), при ручном PLAY аватар уменьшается. Решение: игрок и лобби — x2 (`Balance.Avatar.Lobby`), на время PLAY аватар x1; препятствия и NPC НЕ менялись. Причина: физический масштаб препятствий/NPC обесценил бы все проверенные тесты NPC (27 типов препятствий, расчёты прыжков/зазоров). Скорость и высота прыжка масштабируются как sqrt(scale) / scale (подобие по Фруду). Минус: лобби, подсказки и камера подстраиваются под «великана» (зум 26, табличка PLAY x2). Если нужен реальный физический масштаб, это отдельная большая задача (каталог, модели, Traversal, Brain, валидация, повтор всех тестов).

## D-020 (2026-11-15) — планирование NPC по одной зоне
Периодические ловушки (Fire Trap, Spike Platform) и подвижные преграды (Moving Wall, Prism Spinner) NPC проходит по одной: подойти, замедлиться, встать в точке подготовки (радиус тела + зазор), пройти только если ВЕСЬ проход лежит в безопасном окне (для подвижных — выбрать боковую полосу и симулировать позу препятствия), затем планировать следующую. Попытка пройти ряд стен одним броском невозможна математически (BUG-011: 0 безопасных стартов из 56).

## D-021 (2026-11-15) — ежедневное испытание = «пройти N чужих трасс»
ТЗ 14 не описывает, ЧТО нужно сделать. Выбрано: пройти заданное число разных трасс вручную после принятия испытания; награда — только множитель (никаких новых источников Coins). Стенд испытаний и три таблицы лидеров стоят в центре лобби (`HallService`).

## 2026-11-16
- **D-020 Визуальное направление:** по 6 эталонам владельца отказ от «графит + неон»; яркий кирпичный полигон (шипы Plastic+Studs, дерево, толстая обводка текста). Неон только у опасностей/целей и крошечных функциональных акцентов. Crystal Rush не используется как референс.
- **D-021 Палубы препятствий:** Plastic + шипы, но `CustomPhysicalProperties(0.7, 0.2, 0.5, 1, 1)` (как у SmoothPlastic), чтобы проверенная физика NPC не менялась (подтверждено T-REG-2).
- **D-022 Мобильный UI:** на телефонах/малых экранах (`UIKit.isCompact`) меню — сетка 3 колонки, опорный размер масштаба 1000x540, окна ограничены видимой областью.
- **D-023 Донаты:** только косметика и чаевые, никакой выдачи Coins/преимуществ; незаданный ID = карточка отключена (нельзя «купить» то, чего нет); выдача только сервером (ProcessReceipt с сохранением до подтверждения; пасс проверяется через UserOwnsGamePassAsync).
- **D-024 Иконки из Blender:** рендер командной строкой (`blender -b -P make_icon.py`), потому что MCP-сервер Blender не запущен; скрипт — редактируемый исходник.


## 2026-11-16 (сессия 4)
- **D-025 Стиль интерфейса «яркий симулятор» (UIKit v2):** по эталонам и просьбе владельца «как в популярных играх, без нейрослопа»: глянцевые двухтоновые кнопки с толстым чёрным контуром и бликом, шрифт Fredoka (названия, кнопки, числа) + Builder Sans (мелкий текст), окна с градиентной шапкой, 3D-иконкой и красной «X» на углу, карточки с цветом редкости и огромной зелёной кнопкой цены с монетой, описания по кнопке «i». Общие компоненты `UIKit.itemCard/priceButton/tag/statBars`.
- **D-026 Цены доната:** чаевые 25 / 100 / 500 R$ (шаги ×4 и ×5) + пасс Supporter 49 R$; знак Supporter (косметика) открывается при суммарных чаевых ≥ 50 R$ ИЛИ с пассом (`Donate.SupporterMin = 50`): пасс — самый дешёвый путь к знаку. Карточки показывают живую цену из Roblox, а не число из конфига. Никаких Coins и преимуществ.
- **D-027 Иконки:** один крупный предмет, чёрный контур (Freestyle), без плиты-основания; читаемость проверяется на листе 128 px. Правило: сначала осмотр и сверка с эталоном, потом загрузка в игру.
- **D-028 Компактная раскладка** включается при касании без клавиатуры или `ViewportSize.Y < 420` (раньше 520): ПК-окна высотой 420–520 получают ПК-раскладку.
- **D-029 Оформление мира:** блочные «кирпичные» кусты/деревья/камни вместо гладких шаров, заборы по границам участков, флаги с номером участка (ориентир издалека), стена-обрыв по краю карты с рельефом кирпичных шипов (текстура), плитка воды в бассейне. Всё декоративное без коллизии и без CanQuery; твёрдая только стена по краю (чтобы нельзя было сойти с карты).

## D-030 (2026-11-16, сессия 5) — без дерева

## D-031 (2026-11-16, сессия 5) — хотбар вместо вкладок (T35)

## D-034 (2026-11-16, сессия 5) — чем заменяем дерево: ЦВЕТНОЙ ПЛАСТИК

## D-035 (сессия 6) — стартовая трасса для нового профиля
По скиллу roblox-game-design (быстрый «ага-момент», убирать шаги): новый профиль сразу получает маленькую готовую трассу (`Balance.StarterCourse`), её предметы — в инвентаре (можно переставлять/удалять как свои). Старые профили не трогаются (только `rec.data == nil`).
## D-036 (сессия 6) — обучение = только стрелки (правило владельца)
Владелец: «обучение должно быть просто: тебя ведёт стрелочка, без лишней фигни, и показывает что да как». Никаких карточек/окон: дорожка стрелок на земле, стрелка над целью и у кнопки с 1–2 словами. Шаги выводятся из состояния игрока (переподключение не ломает, ветераны не видят). Где Roblox сам показывает подсказку (ProximityPrompt у таблички/прилавка), стрелка прячется.
## D-037 (сессия 6) — ежедневный подарок за вход
Серия 7 дней, `Balance.Login.Rewards` × (1 + Rebirth), сутки — UTC сервера, пропуск дня = снова день 1, только после первого NPC-забега (не мешать обучению). Новый источник монет (идёт в lifetime, источник `login`); экономически не проверен игровыми тестами.
## D-038 (сессия 6) — киоски магазинов: источник правды = запечённая модель
Правки киосков сессии 5 (масштаб 0.6, пластик, кольца, один продавец) живут только в `WorldAssets.Shops`. Переносить их в код не стали (большой риск разойтись с проверенным видом); вместо этого папка `Shops` помечена атрибутом `HandEdited = true`, и `ShopWorldService.Build(true)` отказывается её перестраивать (нужен явный ключ `"overwrite-hand-edits"`). Проверено клоном модуля: 872 детали до и после.

## D-039 (2026-11-20, S12) — доски лидеров: топ-100 с прокруткой (решение владельца)
Владелец: «доски лидеров должны быть топ 100 чтобы доску можно было листать вверх и вниз». Отменяет вопрос «топ-5 вместо топ-10».
План реализации (S13, первым пунктом):
1. `Balance.Boards.Size` 10 → 100 (LeaderboardService: `GetSortedAsync(false, 100)` — одна страница, лимит API 100). ReadEvery 60 с оставить; проверить бюджет DataStore на 3 доски.
2. Сервер (HallService/LeaderboardService) публикует строки досок клиентам (например, JSON в атрибуте/StringValue `ReplicatedStorage.Boards.<id>` при каждом обновлении), а не пишет текст в SurfaceGui сам.
3. Клиент (новый BoardController): для каждой доски и стороны — SurfaceGui в PlayerGui с `Adornee` = щит и `Face` = Front/Back (SurfaceGui в Workspace не получает ввод), шапка BoardSkin неподвижна, под ней ScrollingFrame на 100 строк (видно ~10, прокрутка колесом мыши и пальцем; ScrollingEnabled, ScrollBar видимая, `ZIndexBehavior`, `MaxDistance` как у SurfaceGuiRange). Медали 1–3 и стиль строк — из BoardSkin.
4. По возможности строка «You: #N» под шапкой (место игрока в топ-100 или «not in top 100»).
5. Popular (курсы онлайн, ≤ 8 игроков) — тот же скролл, данных меньше.
6. Проверки: тестовые 100 записей в Studio (mock), прокрутка `user_mouse_input` scrollUp/Down в Play на ПК, вид на iPhone 7/17 Pro (тач — NOT TESTED в эмуляторе), консоль, производительность (600 строк на клиенте), chief Чекпоинт 1 (вид доски) и 2 (данные + прокрутка).
